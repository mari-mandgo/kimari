# ルーティングモード別 実測（2026-08-08）

同一の入力（`docs/demo-transcript.txt` / 2,448文字の打ち合わせ記録）を、
OrcaRouter の各ルーティングモードとフロンティアモデル直指定で処理し、
原価・所要時間・抽出品質を比較した。

原価は資料の単価表（100万トークンあたり）からの概算。為替は $1 = 155円。

| 指定 | 実際に使われたモデル | 所要 | in / out トークン | 概算原価 | 円換算 | 抽出件数 |
|---|---|---|---|---|---|---|
| `anthropic/claude-opus-5`（直指定） | claude-opus-5 | 99.3秒 | 4,432 / 8,192 | $0.226960 | **約35.2円** | 12件 |
| `orcarouter/auto` | qwen3.7-plus | 104.7秒 | 2,113 / 6,023 | 約 $0.00085 | 約0.13円 | 11件 |
| `orcarouter/fusion-mini` | qwen3.7-flash | 64.0秒 | 2,108 / 8,054 | $0.001110 | 約0.17円 | 10件 |
| `orcarouter/fusion-flash` | qwen3.7-flash | **46.8秒** | 2,108 / 6,135 | $0.000861 | **約0.13円** | 10件 |

## 分かったこと

### 1. 原価が約270分の1になる

フロンティアモデルへ直接投げると1件あたり約35円。ルーターに任せると約0.13円。
**打ち合わせ1件の仕分けが0.13円**なら、月額課金のサービスとして十分に成立する。

ルーターがこのタスクを「定型処理（抽出・分類）」と判定し、
qwen系の安価なモデルへ回している。資料にある「定型処理は1/15のコスト」が、
実測ではそれ以上の差になった。

### 2. 核心の判定は、安いモデルでも変わらない

**追加見積が必要な3件（キッチン移設・洗面所タイル・コンセント追加）は、
全モードで一致して検出された。** 最も重要な判定については、
270分の1のコストのモデルでも同じ結論に到達している。

### 3. ただし「認識のズレ」の検出力には差がある

| | risk の検出 |
|---|---|
| claude-opus-5 | **3件** |
| auto / fusion-mini / fusion-flash | 1件 |

opus は「担当の『そうですね』という曖昧な返答」まで踏み込んで指摘した。
また、キッチン移設について「ガスコンロならガス配管、IHなら電気容量の確認と
配線変更も生じる」と、発言にない派生工事まで列挙している。

つまり、**定型的な仕分けは安いモデルで足りるが、
含みのある会話の解釈には高いモデルの価値がある。**

## 採用する構成（削減施策）

上記から、2段構えにする。

1. **全体の仕分け** → `orcarouter/fusion-flash`（約0.13円・47秒）
2. **認識のズレの精査だけ** → フロンティアモデル
   ただし入力を risk 候補の前後だけに絞るため、トークンは全文の1/10以下になる想定

全文をフロンティアに投げれば35円。
仕分けを安いモデルに任せ、精査だけを高いモデルに絞れば、1円未満に収まる見込み。

**「安いモデルだけ」でも「高いモデルだけ」でもなく、
どこに高いモデルを使うかを実測して決めた** ——これが構成の選定理由。

## 再現方法

```bash
npm run dev
node scripts/compare-modes.mjs
```

# 精度の改善（2026-08-08）

## 見つかった不具合：日付の改変

サンプルを通したところ、施主向け確認書に事実の食い違いが出た。

| | 家具搬入の日程 |
|---|---|
| 元の会話 | 引き渡しの**翌週**土曜日 |
| 施主向け確認書 | 引き渡しの**翌々週**土曜日 ← 誤り |
| 社内保存用記録 | 引き渡しの**翌週**土曜日（正） |

社内保存用は正しく書いたうえで「※概要では『翌々週』と記載あり」と食い違いを
自分で注記していた。つまり入力側に揺れが混ざり、文書ごとに解釈が分かれた。

**記録の食い違いを防ぐための製品が、日付を書き換えてしまうのは最も重い欠陥。**

## 対策

3つの文書生成プロンプトすべてに「事実の扱い（厳守）」を追加した。

- 入力に書かれていない日付・数量・寸法・金額を書かない
- 「翌週」「2口」「600mm」は入力の表記のまま使い、言い換えない
- 入力に無い情報が必要なら、その項目ごと省く。推測で補わない

次回の実行で、同じ入力から日付が正しく転記されるかを確認する。

## 今後の改善案

抽出の段階で日付・数量・寸法を構造化フィールドとして持ち、
文書生成では自由記述させずに転記させる。プロンプトの指示より確実。
