## B. リリースまで（必須）

### B-1. 知らせる仕組み

- [ ] **メール通知**（Resend無料枠を想定）
      - [ ] 施主から相談が届いたとき → 現場を作った人へ
      - [ ] 期限が近い・過ぎたとき → 担当者へ
      いまは KIMARI を開かないと気づけない。
      施主には「担当者に届きました」と出るので、放置されたように見える

### B-2. 安全・運用

- [ ] **Cookieを `secure: true` に戻す**
      `app/api/auth/route.ts` と `app/api/auth/form/route.ts`。
      httpのLAN内確認のために false にしてある。https配下では必ず true
- [ ] **`data/` の置き場所**
      いまはファイル。Vercelでは書き込めないので、永続領域かDBへ
- [ ] **共有リンクの有効期限・失効**
      いまは発行したら永久に開ける。工事が終わっても読めてしまう
- [ ] **音声の保存方針を決める**
      いまは文字起こし後に削除。残す場合は保管期間と削除の仕組みが要る
- [ ] **アップロード容量の上限**
      顔写真は256pxに縮めているが、資料・図面は無制限

### B-3. 実務で困るところ

- [ ] **施主向け文書の表記揺れ**
      文字起こしの誤りが文書に残ることがある（例：「縦側の建具色」）。
      仕分けで直した表記を、文書生成でも固定する
- [ ] **会社の管理**
      いまは会社を作る・コードで参加するだけ。
      メンバー一覧・退出させる・管理者の移譲ができない
- [ ] **見積書の管理**
      一覧・複製・削除・番号の振り直し
- [ ] **打ち合わせの編集**
      仕分け結果を手で直せない。AIが間違えたときに直す手段が要る

- [ ] **契約前（初回〜見積提出）の呼び方と拾い方**
      初回から録音した人は「タタキの見積が作れる」と思う。実際そのとおりに動く。
      `lib/prompts.ts` の段階表で、契約前は「契約がないので差分もない。全部出す」
      としてあり、同じ発言でも 契約前16項目 / 解体後3項目 になる。
      ただし2つ足りない。

      - **言葉が全部「追加見積」**。契約前なのに「追加見積が必要」「追加見積書」と出る。
        `phaseLabel` は打ち合わせごとに持っているので、契約前なら
        「概算の拾い出し」「概算見積書」へ出し分ける
      - **初回は「変更」ではなく「要望」**。`EXTRACT_SYSTEM` の入口が
        「金額に影響する変更か」なので、「対面キッチンにしたい」が cost_impact に
        分類されないと、拾い出しのボタン自体が出ない。
        契約前は要望を拾う指示を足すか、契約前用のプロンプトを分ける

      **ハッカソン提出前には直さない。** デモ動画を「追加見積」の表記で撮り終えており、
      文言だけ変えると会場で動画と実機が食い違う。
